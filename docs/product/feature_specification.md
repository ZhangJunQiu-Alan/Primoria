# Primoria Product Specification

Status: current implementation contract, July 2026.

This document describes the behavior that exists in the active personal
learning product and distinguishes it from future product direction. Runtime
contracts, database schemas, and tests remain the final source of truth. Setup
and deployment belong in the root `README.md`; coding constraints belong in
`AGENTS.md` and `CLAUDE.md`.

## 1. Product goal

Primoria is a long-horizon adaptive learning system for all subjects. It turns a
natural-language learning goal into a grounded course, teaches through mixed
media and interaction, records evidence, updates mastery, and carries durable
learner facts into later Tutor and lesson-generation decisions.

The active loop is:

```text
goal
→ KG positioning or generated-graph fallback
→ course outline and first lesson
→ block-level learning and Tutor interaction
→ quiz / feedback / completion evidence
→ mastery and next-step diagnosis
→ learner-fact extraction
→ better next lesson and Tutor response
```

The current product is personal and account-scoped. Classroom, collaborative
workspaces, agent marketplaces, and collective-intelligence ranking are future
directions, not active runtime capabilities.

## 2. Non-negotiable product rules

1. Provider credentials are server-owned. Primoria never supports client BYOK.
2. Product data is Postgres-first; local JSON is import-only, not a runtime fallback.
3. The Web application owns App/Auth/Course/KG writes and user transactions.
4. The Agent owns Tutor orchestration and durable AG-UI runtime state, not product writes.
5. KG coverage misses may create/reuse a reviewed `gen_*` graph path; KG infrastructure failure must surface safely rather than masquerade as a coverage miss.
6. Learner facts and concept mastery are separate evidence systems.
7. Interactive visualization is catalog-first and all-subject, with structured and sandbox fallbacks.
8. User-facing historical/source content generated by a model is a study aid and must be presented with a verification reminder.

## 3. Active product surfaces

### 3.1 Entry, authentication, and account

- `/welcome` is public.
- `/` is the authenticated Tutor home; signed-out users go through `/login`.
- Email/password identities and sessions live in `users`, `identities`, and `sessions`.
- Auth attempts use server-side rate limits before password hashing/verification.
- Password reset uses one-time hashed tokens and Tencent SES when configured.
- Account/settings surfaces expose preferences and reviewable learner facts.

### 3.2 Cold-start onboarding

Onboarding captures three explicit signals:

1. learning goal;
2. knowledge background (`high_school`, `undergraduate`, or `graduate`);
3. Tutor style (`socratic`, `feynman`, or `euclid`).

The goal is positioned against library KGs. If the subject is outside library
coverage and infrastructure is healthy, Primoria may create or reuse a
generated graph. Onboarding prepares the first course and persists recovery
state so interrupted positioning/building can be retried.

Each saved onboarding choice is also synchronized into one evidence-backed
learner fact. Changing the choice updates that fact; skipping/removing it
dismisses the fact instead of leaving stale personalization behind.

### 3.3 Main Tutor

The only active Tutor runtime is:

```text
Browser CopilotKit UI
→ apps/web/src/app/api/copilotkit/route.ts
→ PrimoriaHttpAgent
→ internal AG-UI POST /agent
→ apps/agent/src/graph.mjs
```

The Web route injects owner identity, course-detail context when relevant,
learner profile, and active learner facts. The Agent selects tools and streams
AG-UI events. The removed `/api/tutor/chat` stack is not a fallback.

Important tool behavior:

- `position_learning_goal`: only main-Tutor entry for creating a course.
- `open_interactive_component`: opens or adjusts a catalog component.
- `render_chat_quiz`: temporary quiz in chat; it does not update course mastery.
- specialized renderers: charts, diagrams, physics, algorithms, math, 3D, waves, graphs, molecules.
- `plan_visualization` → `widgetRenderer`/`stemRenderer`: off-catalog custom widget fallback.

### 3.4 Courses and lessons

A `Course` is an owner-scoped learning path. A `Lesson` belongs to a course,
references KG graph/topic/concept ids, and stores ordered blocks as JSONB.
Courses do not copy the global KG structure.

Course creation:

1. position the goal;
2. choose the graph, start topic, and optional target concept;
3. build the outline as concept-frontier bundles: a mastery snapshot is taken
   once at creation, then the concept prerequisite DAG (in scope) is walked in a
   stable authored order and grouped into lessons of 2–3 unmastered concepts.
   Mastered concepts are skipped at build time, so a partially-known subject
   collapses to fewer/shorter lessons; each lesson persists its `conceptIds`;
4. enqueue the first lesson-generation job;
5. keep later lessons planned and generate lazily.

Ordering is a priority topological sort keyed by authored order
(topic then concept `default_order`); concept `centrality` is only a full-tie
break plus a `[core]` depth marker in the generation prompt, never a primary
sort key. Empty mastery reproduces the authored order exactly.

Lesson titles and descriptions start as deterministic concept-name templates. A
best-effort background model call may rewrite each lesson's title and
description behind an equality write fence; failures keep the templates and do
not invalidate course creation.

The lesson reader at `/course/[id]` renders one block step at a time. Course
Tutor is a collapsible right rail scoped to the current course, lesson, visible
blocks, selected block, and selected text.

### 3.5 Lesson blocks

Core block types are:

| Type | Purpose |
| --- | --- |
| `text` | hook, roadmap, explanation, example, summary |
| `analogy` | map an unfamiliar concept to a familiar structure |
| `image` | static cognitive anchor from a user-agnostic image brief |
| `visual` | interactive mechanism, process, relationship, or simulation |
| `quiz` | concept-closing evidence |
| `code` | editable/runnable Python or JavaScript for code-eligible topics |
| `transfer` | integrated or cross-domain application |
| `mind_map`, `slide`, `worksheet` | additional structured learning formats |

Code is not a default decoration. It is eligible for programming, algorithms,
software/Web engineering, numerical/scientific computing, implementation-heavy
machine learning, or an explicit request to write/run code. The bare word
“实现” is not sufficient code intent.

Generation aims for short teaching loops with no more than two consecutive pure
text blocks. Image plus visual usually occupies 30–45% of a lesson, but every
media block needs a distinct teaching purpose. Each concept should close with
its own quiz rather than moving all checks to the lesson end.

### 3.6 Quiz, events, mastery, and next-step decisions

Course quiz submissions use a client `submissionId` plus a database uniqueness
constraint so retries cannot duplicate attempts or learning evidence. Quiz
attempts and learning events are owner-scoped.

Lesson completion enqueues a recoverable `learning_progress_job`:

1. read per-concept quiz evidence;
2. update `user_concept_mastery` using explicit rules;
3. diagnose the next action;
4. persist a recommendation for learner confirmation before remediation work.

Mastery states are `untested`, `weak`, `learning`, and `mastered`. Mastery is
based on quiz/evidence rules; a chat claim such as “I understand” cannot by
itself mark a concept mastered.

### 3.7 Learner profile and facts

`learner_profiles` stores explicit cold-start choices and onboarding lifecycle.
`learner_facts` stores durable statements in four categories:

- `preference`;
- `prior_knowledge`;
- `learning_gap`;
- `goal`.

Facts come from onboarding synchronization or the post-lesson Extractor worker.
Every fact carries confidence, evidence, occurrences, and active/dismissed
status. Dismissal is a tombstone: extraction must not silently recreate the
same fact. Tutor and planner prompts receive only active teaching-relevant
facts (`preference`, `prior_knowledge`, `learning_gap`) with a bounded count;
goals remain profile context and do not contaminate unrelated course content.

The Extractor does not update mastery, decide remediation, create lessons,
replace KG positioning, or generate “perfect notes.”

### 3.8 Interactive visualization

Visualization uses three ordered layers:

1. **Declarative catalog:** 19 pre-engineered React components across STEM,
   humanities, language, social science, geography, art, music, and psychology.
2. **Specialized structured renderers:** chart, Mermaid, physics, algorithm,
   math, 3D, wave, graph, and molecule representations.
3. **Sandbox fallback:** custom self-contained HTML/CSS/JS fragment after
   `plan_visualization`.

For a catalog component, the main Tutor chooses `componentId` by calling
`open_interactive_component`. The browser card calls authenticated Web stage 2,
which creates a full config or applies a minimal patch and validates the result
with Zod. Student controls and natural-language adjustments update the same
config object. The Agent never sees concrete config values.

Catalog misses and render outcomes are recorded as `visualization.render`
events. The allowlisted internal analytics page aggregates sandbox topic demand
and per-component reliability. A fixed 28-case routing fixture protects
cross-subject, vague-adjustment, off-catalog, and chat behavior.

### 3.9 Course sharing and media assets

Course share links store immutable sanitized snapshots. Public share pages and
imports read the snapshot, not live owner rows. Revoking and re-enabling a share
creates a new token; imports are idempotent per learner.

Generated lesson images use a global cache keyed by user-agnostic brief
semantics. Learner facts must never enter image briefs. `owner_id` remains a
reserved private-media channel with no current lesson-image writers.

## 4. Knowledge graph contract

- A concept is the smallest independently diagnosable skill/outcome.
- Topics normally contain a small coherent concept set (authored as 2–3
  concepts); they order and group concepts but are no longer the lesson unit.
  Lessons are concept-frontier bundles drawn from the concept prerequisite DAG.
- Runtime edges are prerequisite edges (`hard` or `soft`) and must form a DAG.
- Concept ids are globally unique; cross-topic and cross-subject prerequisites are allowed.
- `default_order` guides a stable topic path but does not override prerequisite correctness.
- Source graphs live under `data/knowledge-graphs/source`; generated candidates live under `data/knowledge-graphs/generated`.
- KG source import and embedding initialization are separate from schema bootstrap.

## 5. Ownership and durability

Primoria follows a modular-monolith-plus boundary:

| Owner | Responsibilities |
| --- | --- |
| `apps/web` | UI, auth, product APIs, App/Auth/Course/KG transactions, course generation, interactive configs, workers |
| `apps/agent` | LangGraph/deepagents orchestration, AG-UI streaming, run leases/retries/cancellation/checkpoints |
| PostgreSQL | product state, KG/pgvector, job queues, Agent runtime state |
| `packages/contracts` | shared artifact/tool/dependency/catalog contracts |

Long-running lesson generation, learning progress, and fact extraction use
Postgres leases, fencing tokens, heartbeats, bounded retries, and explicit
failed states. Agent retries are conservative: work is automatically retried
only before user-visible/tool output, preventing replayed side effects.

## 6. Current non-goals and roadmap

Not active today:

- classroom/teacher assignment and class analytics;
- collaborative workspace rooms;
- user-created Tutor agents or an agent marketplace;
- cross-user system memory and ranking;
- vector episodic memory and generated “perfect notes”;
- automatic persistence/reuse of arbitrary sandbox widgets as apps;
- broad multimodal input beyond current attachment handling.

Near-term hardening:

1. close the remediation/resume loop across same-graph and cross-graph prerequisites;
2. improve fact extraction, evidence review, correction, and decay;
3. use real visualization analytics before expanding the catalog;
4. deepen humanities interaction such as annotations and future map linkage;
5. maintain route, schema, worker, bundle, DB, and browser regression gates.
