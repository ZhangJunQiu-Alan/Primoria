Onboarding Facts Intake 已进入当前实现

本节是对 2026-07-17 审查基线的后续补充；下方原始门禁数字和风险判断保留其历史语境。

状态：后台直接写入，Onboarding 不等待模型

第二步已从知识背景选择替换为可跳过的自由文本输入。POST /api/onboarding/facts 只在事务内创建或复用 owner 唯一的 active profile_fact_intake_jobs、写入 pending 并返回 202；页面立即进入 Tutor Style。Settings 的文本导入复用同一队列和 owner-scoped 状态查询。

共享 Extractor Worker 优先消费 profile intake，再处理 lesson extractor job。它最多保存八条有精确原文 quote、置信度至少 0.8 的事实，分类固定为 preference、prior_knowledge、learning_gap、interest、goal、profile_context；无法安全归类或无长期价值的内容进入 ignore，不会动态创建类别。

写入保持 active 语义去重、dismissed tombstone、job-evidence 幂等、lease heartbeat 与 fencing。成功或永久失败均清除临时原文。自述事实不会写 mastery、不会跳过 KG 内容，也不会扩大课程覆盖；knowledgeBackground 只从明确教育阶段证据派生。

Executive view

整体概览

架构主方向正确，且已从“开发原型”跨到“可受控运行的模块化单体”。当前最大风险不再是是否能持久化，而是新链路的身份、成本、恢复与负载边界是否完整。

结论：适合受控灰度，不建议在修复前直接放大公开流量

Web 继续拥有业务规则、App/Auth/Course/KG 数据写入与事务边界；Agent 负责 Tutor 编排，并把运行、事件、租约和 checkpoint 放入独立的 agent_runtime schema。这个边界符合此前选择的“模块化单体+”，没有必要为了形式上的先进性拆 Redis、Kafka 或微服务。

旧报告的关键阻断项已经被实质关闭：生产 Agent 不再使用 dev server/内存 checkpoint，测验写入具备幂等键，队列采用租约 fencing，容器与数据库角色已隔离，健康检查覆盖 DB/KG/Agent/worker，生产依赖无高危或严重漏洞，课程分享也已是真实快照实现。

当前最高优先级是修复同类交互组件互相覆盖的问题，并补上交互配置接口的用户级成本控制与 Agent 内部调用鉴别。之后再处理 Agent 运行数据保留、恢复演练和轮询负载。教育产品层面，mastery 仍是单次测验规则，而不是可信的长期学习模型。

Open findings

当前主要问题清单

没有发现新的 P0。P1 表示应在公开放量前处理；P2 可以排入后续迭代，但不应长期忽略。

P1 · BUG

同一 componentId 的多个交互卡会互相覆盖状态

模块级 instanceStore 只按 componentId 存 config。历史中同时存在两张 physics.lens-imaging 卡时，后挂载的卡会覆盖前一张；后续“调大一点”可能基于错误实例生成 patch。

后果：用户调整错误对象，历史卡片重挂载后行为不确定，属于可复现的身份建模缺陷。

interactive-component-card.tsx:14-23, 48, 74, 89, 142
更安全：把 AG-UI tool call / artifact ID 作为稳定 instanceId，按实例保存 config；调整请求必须显式引用目标实例。
P1 · COST

交互 config LLM 接口缺少用户级限流与并发预算

接口虽然要求登录并限制 prompt 长度，但每次请求都可触发最长 30 秒的模型调用。当前只有 auth route 使用数据库 rate limit，交互接口没有用户配额、并发槽位或请求幂等。

后果：一个已登录账户或脚本即可制造无界模型费用与并发压力；current 只做通用 record 校验，也会被原样拼入模型 prompt。

api/interactive-component/route.ts:13-36
interactive/configure.ts:35, 60-67
优先使用 PostgreSQL 计数窗口 + 每用户并发锁，不需要现在引入 Redis。
P1 · TEST

交互路由评测没有覆盖生产 Tutor 的真实决策路径

生产 stage-1 是 Agent 模型对 open_interactive_component 的 tool choice；现有 28 条 fixture 在 --validate-only 下只校验 JSON 和组件 ID，真实评测调用的是另一套 Web selectInteractiveComponent helper。CI 也未显式运行 catalog:validate。

后果：报告可以显示 fixture 合法，但 Tutor prompt、tool schema 或模型路由已经退化而 CI 仍然绿色。

eval-interactive-routing.ts:5-6, 29-38
.github/workflows/ci.yml:41-57
需要生产 prompt/tool 契约的确定性测试，并将真实模型路由评测设为定时或发布前门禁。
P1 · TRUST

Agent 内部 HTTP API 没有服务间鉴别或 owner 约束

/agent、run status 和 cancel 接口接受内部网络请求，没有共享密钥/HMAC；ownerId 又从请求 body 的 state/metadata 推导。端口未公开降低了风险，但不能把 Compose 网络等同于身份。

后果：内部 SSRF 或任一被攻陷容器可伪造 owner、创建 run、读取状态或取消已知 run ID。

apps/agent/src/server.mjs:112-129
run-store.mjs:11-16, 38-39
当前规模用 Web→Agent 共享 secret + HMAC 签名 owner/run 即可，mTLS 暂无必要。
P1 · SCALE

每条 SSE stream 以 100ms 固定周期轮询两次数据库

stream loop 每 100ms 查询 events 和 run status，空闲时也不退避。单连接约 20 次查询/秒；100 个并发 Tutor stream 理论上会产生约 2,000 QPS 的纯投递轮询。

后果：模型并发还没达到瓶颈前，数据库可能先被空轮询占满；当前没有 Agent stream 负载测试证明上限。

apps/agent/src/server.mjs:63-81
短期采用活动期 100ms、空闲指数退避和合并查询；中期评估 PostgreSQL LISTEN/NOTIFY，无需 Kafka。
P1 · DATA

Agent 运行与可视化原始文本没有自动保留策略

Agent runs 的 input 和 events 保存完整消息/tool 输出；可视化 telemetry 也保存最多 300 字的原始 topic。虽然有手动 agent:runs:prune，Compose、CI 和脚本中没有定时执行者。

后果：数据无限增长，隐私保留期不明确，内部 analytics 会沉淀用户可能输入的个人信息。

agent_runtime.runs.input / events.event
runtime/admin.mjs:25-27
api/telemetry/visualization/route.ts:9-35
定义 30/90 天分层保留，定时 prune，并对 analytics topic 做摘要或脱敏。
P1 · RECOVERY

恢复演练没有验证新的 agent_runtime 与 checkpoint 数据

远端备份、checksum 和隔离 restore 已存在，但恢复脚本只对 8 张 public 表做 count。没有检查 agent_runtime.runs/events 或 LangGraph checkpoint 表。

后果：当前“恢复成功”不能证明 durable Agent 真正可恢复，最核心的新持久化能力仍可能在灾难恢复中丢失。

scripts/pg-restore-drill.sh:65-69
按 schema 校验关键表、约束与少量关系完整性，并在恢复库上执行一次 run/checkpoint read smoke。
P1 · SECURITY

Web 边缘安全基线仍不完整

密码 hash/verify 在请求线程使用同步 pbkdf2Sync；Next/Caddy 没有统一 CSP、frame、MIME 与 referrer headers；多条课程 API 仍把任意 error.message 返回给客户端，并用字符串匹配判断 404。

后果：并发登录可阻塞事件循环，浏览器防护依赖默认行为，底层 SQL/provider 错误可能泄露且 HTTP 状态不稳定。

auth/password.ts:1-22
next.config.ts:5-19
docker/caddy/Caddyfile:5-8
courses/[id]/chat/route.ts:156-159
先改异步 KDF、typed domain errors 与基础 headers，再评估 Argon2id 迁移。
P1 · INTEGRITY

App schema 的状态字段与数值边界仍主要靠应用代码

lesson role/status、多个 job status/stage、quiz score/total、mastery status 等仍是普通 text/integer。Agent runtime 已有 status/attempt CHECK，App schema 没有保持同等标准。

后果：脚本、迁移或未来新写入路径可产生不可能状态；错误数据会让 worker claim、UI 分支和统计悄悄失真。

apps/web/src/lib/db/schema.ts:191-225, 335-346, 387-398, 430-439
为有限状态使用 enum 或 CHECK；为 score/total/progress 添加范围和交叉约束，并先跑数据审计。
P2 · PRODUCT

交互工具只传“原始短句”，对省略上下文的请求不鲁棒

tool schema 强制把 learner request verbatim 交给 Web stage-2。对于“把刚才那个过程做成可交互的”这类省略主语的创建请求，stage-2 看不到课程/对话上下文，只能猜测具体教学内容。

后果：组件类型可能选对，但 config 内容发生幻觉；adjust 有 current config 缓解，create 没有。

prompts.mjs:82-87
schemas.mjs:105-113
让 Agent 传受限的 resolved_request，保留原始 request 用于审计，不要把完整聊天或 learner facts 直接复制过去。
P2 · FLAKY

Mermaid parser worker 在资源竞争下会撞固定超时

全量 Web 测试与多个门禁并行时，2 个 Mermaid 测试在 30 秒超时；隔离重跑同一文件 11/11 在 2.94 秒通过。功能没有稳定回归，但测试对机器负载敏感。

后果：CI 资源抖动会制造假红，真正 parser 问题也可能被团队误判为偶发。

tests/mermaid-validation.spec.ts
区分 worker 启动超时与 parse 超时，增加启动握手；CI 避免与重型 build 同机争抢，保留一次受控 retry 仅用于诊断。
P2 · DEBT

维护热点、运行版本漂移与 KG 来源治理仍偏弱

globals.css 仍有 9,798 行，library grid、i18n 字典和 Copilot hook 超过 1,000 行；Docker 是 Node 20，CI 是 Node 22，runtime image 复制完整源码与依赖树。KG 有 23 个 JSON 文件，但没有 source-map sidecar 或等价的 concept-level provenance。

后果：局部修改的回归半径扩大，生产/CI 行为可能分叉；教育内容无法回答“来源、审核人、版本、适用范围”。

globals.css: 9,798 lines
Dockerfile:6,29 vs CI node-version:22
data/knowledge-graphs/source: 23 JSON / 0 source maps
按纵向功能切片拆热点文件，统一 Node 主版本，并引入轻量 provenance manifest。

错误处理

不要在 route 内用字符串匹配决定状态码，也不要把任意异常消息透传。

unknown error → log(error, requestId) → map typed error → stable code + safe message

事务与 outbox

已有测验路径是正确样板：业务事实与后续 job 在同一事务落库，worker 异步消费。

BEGIN → write learning event → enqueue extractor/progress job → COMMIT

API 契约

route 入口使用 Zod 是正确的，但内部状态也应先按目标 component schema 校验，再进入 LLM prompt。

auth → rate budget → parse envelope → parse component config → invoke → validate → respond

可观测性

健康检查和结构化 LLM usage 已有基础；下一步是 request/run/job 关联 ID、延迟分位数、失败类别和成本聚合。

requestId ↔ runId ↔ jobId ↔ model usage ↔ user-safe error code

Plain-language glossary

关键词解释

这些词在行动清单里反复出现。解释以 Primoria 当前行为为准，而不是抽象定义。

模块化单体+

仍是一个仓库和一套主要数据库，但 Web、Agent、contracts、worker 各自有明确所有权；后台任务可靠性按生产系统标准处理。

Outbox

业务数据与“稍后要做的任务”在同一事务提交，避免业务成功但后台任务丢失。当前 quiz → extractor enqueue 已采用这一思想。

Fencing token

worker 每次领取任务获得新 lease token，旧 worker 即使恢复也不能覆盖新 worker 的结果。

HMAC

Web 用共享密钥为内部请求签名；Agent 可验证请求确实来自 Web，且 ownerId/runId 没被篡改。

LISTEN/NOTIFY

PostgreSQL 自带的轻量通知机制。Agent 有新 event 时唤醒 SSE，不必每 100ms 空查数据库。

BKT / IRT

分别用于估计知识掌握概率和题目/能力关系。它们需要足够真实数据；当前更适合先做可解释的 evidence-aware mastery。
