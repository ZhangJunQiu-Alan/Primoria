建课 Agent 到底在做什么

一句话：它不是让一个聊天机器人一次写完整门课，而是一条分工流水线。先理解你的学习目标， 再在知识图谱里定位，从课程大纲开始，逐节生成 lesson，并用校验、断点和后台任务保证质量。

    关键设计细节

    这部分回答几个最容易混淆的问题：Agent 是一个聊天机器人吗？Planner 和 Writer 有什么区别？ 为什么视觉块和图片块要分开？为什么失败后可以恢复？

    Agent 在这里是什么意思

    这里的 Agent 不是一个单独的聊天窗口，而是一组被编排的任务：定位、建大纲、排队、规划 lesson、 写 block、生成图片、校验、保存。每一步有自己的输入和输出。

    为什么不一次生成整门课

    因为整门课太长、太容易跑偏，也不方便失败恢复。现在先生成课程大纲，再逐节生成 lesson。 用户打开当前 lesson 时，只需要当前 lesson 的 blocks；下一节只做预热。

    课程大纲和 lesson 内容不是一回事

    大纲只告诉系统这门课有哪些 lesson，以及每节 lesson 大概讲什么。真正的正文、quiz、image、visual 会在 Lesson Job 里生成。这样课程列表可以先稳定存在，内容则按需要逐节生产。

    关闭页面不会停止生成

    生成 lesson 的工作在后台 worker 里跑，不依赖浏览器页面。页面只是发起任务和查看状态。 这也是为什么 job store、lease、checkpoint 很重要。

    Planner 只负责结构

    Planner 看 KG、掌握情况、用户资料和 lesson 目标，产出一个紧凑计划：这节课需要哪些 block， 每个 block 讲什么目标，用什么类型，以及给 Writer 的简短指令。

    • 不写大段正文。
    • 不生成最终图片。
    • 不让模型自由决定 visual engine。

    Writer 只负责内容

    Writer 不能重新规划课程。它拿到 Planner 的 block job 后，按照顺序补齐内容字段： text 写 markdown，quiz 写题目，visual 写对应 payload，image 写图片 brief。

    • 不增删 block。
    • 不改变顺序。
    • 出错后按精确错误修复。

    这条链路按阶段保存进度。可以把它理解成游戏存档：Planner 计划成功后存一次，Writer 每批 block 成功后也存一次。失败重试时，不需要从头重新做所有事。

    Lease 是什么

    Lease 可以理解成 worker 的临时工作证。只有持有当前有效工作证的 worker 才能推进和发布 lesson。 如果旧 worker 卡住或超时，新 worker 可以接手，旧 worker 不能再把过期结果写回去。

    为什么图片失败不一定让整节课失败

    图片是增强理解的媒体资产。当前设计允许单张图片生成失败后变成错误占位，但整节 lesson 不会因此全部失败。 这能避免因为一个媒体调用拖垮完整课程。

    一节 lesson 不是随意堆文字，而是由有角色的 blocks 组成。常见的两概念 lesson 会围绕 intro、example、 image、visual、quiz、transfer、summary 展开。Validator 会检查数量、顺序、覆盖、媒体比例和字段结构。

    Text 解释、例子、路线、总结。负责把概念说清楚。
    Analogy 用熟悉事物类比抽象概念，降低理解门槛。
    Image 静态直观锚点。先写 brief，再由图片阶段生成资产。
    Visual 可交互机制。用于变量关系、过程观察、算法演示。
    Code 只在适合代码的学科或用户明确需要代码时出现。
    Quiz 每个 concept 收尾检查一次，用于后续掌握度判断。
    Transfer 把多个概念合在一起，迁移到新场景。
    Summary 课后反思和小结，帮助形成完整学习闭环。

    给非技术用户的最终理解：Primoria 的建课不是「模型随口生成一堆内容」，而是「知识图谱定位 + 课程骨架 + 后台逐节生产 + 结构化验收」。模型只负责它擅长的部分，系统负责边界、顺序、恢复和发布。
